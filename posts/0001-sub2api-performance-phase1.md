# 第一阶段性能排查

检查时间：2026-09-15 10:22–10:30，Asia/Shanghai。只读排查，未改变模型、推理强度、上下文、调度优先级、并发或线上部署。全部 8 个现有账号 priority=1、concurrency=3。

## 结论

1. 暂无证据支持提高并发、淘汰某账号或换代理。24 小时系统分钟采样的排队深度最大值为 0；这不排除采样间的短时等待。
2. 首 Token 延迟与模型/推理强度、上下文大小共同变化。不能将承接较重请求的账号简单标为慢账号。
3. 本机开发验证和 Docker 构建确实造成资源高峰，但当前部署期请求样本过小，不能承诺迁移构建能把 10 秒 TTFT 降到某个数值。
4. 长请求的总耗时主要是持续输出：最近 5 个最长请求平均输出速度约 32.5–33.3 Token/秒。
5. 下一步优先隔离开发验证/镜像构建与线上推理资源，并补充分阶段时延观测；保持效果的前提下，再用同模型同上下文样本判断上游或账号差异。

| 模型/推理记录 | 请求数 | TTFT 平均 | TTFT P95 | 总耗时平均 |

| gpt-6-astra / high | 233 | 4.70s | 8.46s | 18.84s |

上下文分组使用 `input_tokens + cache_read_tokens`，即本项目用量日志中的非缓存与缓存输入之和；不等价于独立测量的完整客户端上下文。

| 上下文输入量 | 样本数 | TTFT 平均 | TTFT P95 |

## 部署与资源

与 systemd 实际部署进程日志对齐，剔除了部署自测中的假部署消息：

- 09:44:27–09:47:33
- 09:58:30–10:01:37
- 10:18:25–10:21:41

09:20 以后，gpt-6-astra/high：部署窗口内 8 条，TTFT 平均 4.69s、中位数 4.25s；窗口外 72 条，平均 4.52s、中位数 4.04s。输入量均值约 111k 与 106k，不是严格对照实验。

高 CPU（≥70%）分钟关联样本 13 条，TTFT 平均 5.06s；其他 68 条约 4.50s。此关联同样不能证明因果；资源分钟采样也不能还原每个请求开始时的瞬时负载。

普通空闲分钟 CPU 多为 4%–6%、内存约 15%–20%；本地开发验证/构建期间 CPU 可达 90%–96%，内存峰值约 88%。09:41 的一次 11.19s TTFT 与 CPU 90.6%、内存 86.6% 的本地构建验证时段重合；09:29 的另一次 10.14s TTFT 出现在 CPU 约 5% 且输入约 204k 时，说明资源争用并非全部原因。

Docker 构建在业务机执行，未见独立 CPU/内存资源上限。仅降低部署脚本进程的 nice 值不保证限制 Docker daemon/BuildKit 执行的构建，不能把它当作有效隔离。

## 线路和流式传输

- 本地 `/health` 三次总耗时约 0.7–1.0ms。
- 经服务器自身公网域名访问 `/health` 三次约 30–67ms；不能代表用户所在地到服务器的链路。
- 对上游 `/backend-api/codex/responses` 做三次不带认证的 GET 探测，HTTP 405，TLS 完成约 27ms，首响应约 72/88/316ms。未调用模型、未消费账号推理额度。
- 这些只是连接和边缘响应测试，不能测出认证后模型队列、推理准备或真实推理 RTT。
- Nginx HTTP/1.1 转发、`proxy_buffering off` 已启用，未发现响应缓冲导致的明显等待。
- 成功请求没有完整 auth/routing/connect/upstream 分阶段字段；当前 TTFT/Duration 由上游转发路径计时，不应直接当成完整客户端端到端耗时。

## 错误与重试

近 6 小时记录到一次上游 429（10:21:21，账号 6）。24 小时有历史上游 503、429、401 等事件及路由失败，不能简单与当前一小时成功率相混。

以 request_id 关联成功日志与错误日志未找到匹配，说明当前数据不足以精确重建成功请求中的重试链，不表示从未重试。系统分钟采样存在账号切换记录。

## 下一步执行顺序

1. 将前端检查与镜像构建移出业务机，在 GitHub Actions 构建固定提交的镜像；保留本地健康评分补丁、镜像版本校验、备份、健康检查和回滚。需单独落地验证镜像传输/拉取路径，不能仅删掉服务器构建。
2. 成功请求补充分阶段耗时（排队、连接、上游首事件/首内容、重试次数）及结束原因；不记录提示词、令牌或密钥。首事件与首可见内容要区分，避免把 SSE 心跳当成首次回复。
3. 对同模型、同推理强度、相近输入规模的 P50/P95 与输出速度做前后对比。每组积累至少约 30 个自然业务样本作为初步参考，同时保留样本量与时间范围；不用少量样本的 P99 评价账号。

本阶段没有修改生产配置或部署流程，也没有压测、主动推理、强制轮换账号或降低模型效果。下一阶段的隔离改造应以降低资源争用为目标，不承诺在现有数据下无法证明的延迟降幅。
